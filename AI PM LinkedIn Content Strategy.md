## Engagement Strategy

**Comment reply protocol for each post:**
- Reply to ALL comments within 90 minutes of posting (algorithm boost window)
- Don't just say "thanks" — add value ("Great question — I'd add that when latency exceeds 2s, we fall back to…" or "Here's the specific eval we use for that case")
- Pin your own follow-up comment with one extra insight or a link to further reading
- End replies with a question to keep the thread alive ("What's your team's threshold on that?")

- Tag 1-2 relevant influencers per post (not spam — only when your post genuinely extends their work)

- Repurpose top-performing posts as LinkedIn documents after 2-3 weeks

**Growth mechanics:**
- Post 3x/week consistently for 90 days minimum
- LinkedIn in 2026 rewards platform-native creators with reach
- Carousels earn 7% avg engagement; use them for your highest-signal content

## What Hiring Managers Actually Notice

Based on cross-referencing the 892 JD analysis with influencer insights:

1. **Eval design posts** — immediate credibility signal. If you can write an eval, you can do the job.
2. **Shipped artifact posts** — screenshots, metrics, user counts. "I launched X that serves Y users with Z% quality" beats any framework post.
3. **Failure posts** — engineers and PMs trust someone who has broken things. Show your scar tissue.
4. **Technical depth** — comments that show you understand transformers, context windows, token math. Not academic, but operational.

**Posts that DO NOT help:** "10 AI trends in 2026" (everyone posts this), motivational quotes, generic PM advice without AI specificity, hot takes without data.

## Week 1: Ready to Post

### Post 1: Mon — The Eval-First Workflow

Format: Text + image (screenshot of an eval rubric or a clean framework graphic)

Hook: "The single question that separates AI PMs from 'PMs who touched AI': design an eval for a chatbot. Here's my framework."

The eval-first workflow is simple but most teams skip step 1:

1. **Define the quality bar before writing a prompt.** What does "good" look like? Write 3 example Q&A pairs by hand. That's your golden set.

2. **Build a rubric.** Accuracy, tone, safety, completeness. Score 1-5. Pass threshold: 4/5 average, no single score below 3.

3. **Write the eval suite.** 50 golden set pairs + 50 adversarial cases. Run against your baseline (prompt-only, no RAG).

4. **Set rollback triggers.** If eval pass rate drops below 85% or hallucination rate exceeds 2%, block the deploy.

5. **Calibrate with users.** Offline evals correlate ~60% with user satisfaction. But without them you're shipping blind.

The order matters: define quality → write eval → build feature. Not the other way.

### Post 2: Wed — Eval Rubric Template (Carousel)

Slide 1 — Title: "The Eval Rubric I Use for Every LLM Feature"

Slide 2 — The problem: "Everyone asks 'which model is best?' No one asks 'what does good look like?' Start here."

Slide 3 — Rubric dimensions: Accuracy (1-5), Tone (1-5), Safety (1-5), Completeness (1-5), Adherence to constraints (1-5)

Slide 4 — Golden set structure: 50 ideal Q&A pairs written by hand. 25 edge cases. 25 adversarial inputs. Include the "why this is right" for each.

Slide 5 — Scoring: 4+/5 average to pass. No single dimension below 3. Automatic fail on safety < 4.

Slide 6 — Rollback plan: Pass rate < 85% → block deploy. Hallucination flagged → rollback. User satisfaction drops 10% → re-eval.

Slide 7 — Key insight: "Your eval is a product. Version it. Review it. Update it as user behavior changes."

### Post 3: Thu — Eval Failure Story

Format: Text + image (a graph showing metric divergence)

Hook: "Our eval passed at 94%. Users hated the feature. Here's why offline evals lie and what I learned."

We shipped a Q&A feature with 94% eval pass rate. Users gave it 2/5.

Post-mortem findings:
- Our golden set matched our writing style, not user questions
- We tested on clean inputs; production was messy, ambiguous, multi-intent
- Adversarial cases were too obvious — real failure modes were subtle

Fix: Revamped golden set from 50→200 pairs using actual user logs. Added a "clarity" dimension. Iterated 3 rounds.

Offline evals are necessary. But they're a proxy, not the truth. Calibrate against user experience, not your rubric.
